# План проекта: симулятор сборки ПК

Рабочее название: `petproject`. Веб-приложение, где пользователь собирает компьютер из комплектующих и сразу видит, совместимы ли детали, что потянет сборка и почему. Каждая деталь и каждый термин объясняются простым языком. Проект учебный и для портфолио (позиция Go-разработчика): попутно осваиваем веб, базы данных, аналитику, микросервисы и инфраструктуру.

Подробный концепт со схемой и словариком: [документ «Симулятор сборки ПК: концепт и дорожная карта»](https://claude.ai/artifact/GWd63SAx42pfm3JPMD8RUe).

## Цели

1. Научиться понимать устройство компьютера: из чего состоит, что зачем, как выбирать детали.
2. Дать новичку собрать ПК в симуляторе с проверкой совместимости, оценкой и понятными объяснениями.
3. Через проект выучить Go-бэкенд и сопутствующие инструменты на уровне собеседования (джун, джун+, мидл).

## Функциональные требования

### Вводный урок
- Тур «Из чего состоит компьютер» перед первой сборкой: по каждой части «что это, зачем, с чем соединяется».
- Кнопка «А это зачем?» на любом шаге сборки, плашка «Что важно при выборе» в начале шага.
- Всплывающие подсказки на каждом термине (сокет, чипсет, TDP, VRAM, CPU, GPU и т. д.).
- Тексты уроков и подсказок хранятся в БД и отдаются через API.

### Сборка и совместимость
- Пошаговый выбор: процессор, материнская плата, память, накопитель, видеокарта, блок питания, корпус, охлаждение.
- Проверки: сокет, тип памяти, мощность блока питания с запасом, габариты (длина видеокарты, высота кулера, форм-фактор платы).
- Статус «работает / чего не хватает» до сбора минимального набора.

### Оценка и «что потянет»
- Своя упрощённая модель «очков производительности» у процессора и видеокарты, требуемые очки у игр и сценариев (стрим).
- Общая оценка, сообщения «теперь можно сыграть в …», «теперь можно стримить», поиск узкого места.

### Замена детали
- Пометка «нет в наличии» и кнопка «Найти замену»: «чуть слабее и дешевле», «похожее», «чуть мощнее».
- Только детали в наличии и совместимые с остальной сборкой; у каждого варианта видно, что изменится в очках, цене и играх.

### Ноутбуки
- Шум кулеров в дБ с бытовыми сравнениями, вес и габариты («как два пакета сахара», «влезает в ручную кладь»), глянец или мат, материалы корпуса.

### Цены, бюджет и отзывы
- Цена сборки, лимит бюджета, история цен, «сейчас выгодно брать».
- Отзывы пользователей внутри приложения (оценка, шум, нагрев, плюсы и минусы) и подсказки на их основе. Чужие отзывы с сайтов не собираем.

### Самопроверка и помощник
- Квизы по деталям и терминам.
- ИИ-помощник: кнопка «Спросить», короткий ответ модели Claude по данным каталога.

### Прочее
- Регистрация и вход, сохранённые сборки, сравнение двух сборок, ссылка на сборку. Данные каждого пользователя изолированы.

## Схема данных (набросок)

```
manufacturers(id, name, country, about)
components(id, type, manufacturer_id, model, price_minor BIGINT,
           perf_score INT NULL, in_stock BOOL, specs JSONB)
glossary(id, term, explanation)
lessons(id, step, part_type, title, body)
games(id, name, need_low INT, need_mid INT, need_high INT)
users(id, email, password_hash, ...)
builds(id, user_id, name, created_at)
build_items(build_id, component_id)
price_history(component_id, day DATE, price_minor BIGINT)
reviews(id, user_id, component_id, rating, noise, pros, cons, created_at)
quiz_questions(id, topic, question, options JSONB, answer)
quiz_answers(id, user_id, question_id, correct BOOL, answered_at)
```

Решения:
- Деньги хранятся целыми в минимальных единицах (копейки, `int64` / `BIGINT`), никаких `float64`.
- Характеристики деталей разные по типам, поэтому лежат в `specs JSONB`; часто фильтруемые поля (тип, цена, очки) вынесены в обычные колонки.
- Каталог на старте заполняется вручную (5–10 деталей на категорию); для нагрузки и аналитики есть генератор синтетики. Характеристики берём с официальных сайтов производителей, чужие таблицы бенчмарков массово не копируем.

## Архитектура

До этапа 7 это монолит с чёткими модулями, которые потом выделяются в сервисы:

```
cmd/server/            точка входа
internal/catalog/      детали, производители, глоссарий, уроки
internal/compat/       движок правил совместимости
internal/scoring/      очки, «что потянет», узкое место
internal/builds/       сборки пользователей, замена детали
internal/prices/       история цен, аналитика
internal/reviews/      отзывы
internal/quiz/         квизы
internal/auth/         регистрация, вход
migrations/
web/                   фронтенд
```

Слои: handler → service → repository, зависимости передаются через интерфейсы.

Целевая схема после этапа 8: браузер → API gateway → сервисы `users`, `catalog`, `builder`, `quiz` (между собой gRPC), `prices` → Kafka → `notifications`, позже `assistant`. Под всем этим Prometheus, Grafana, Jaeger, Kubernetes.

## Дорожная карта

На каждом этапе: код, тесты, обновление README и мини-собеседование из 3–5 вопросов.

0. **Каркас.** `go mod`, HTTP-сервер, `chi`, `/health` и `/ready`, `slog`, конфигурация из окружения, graceful shutdown, Dockerfile, `docker-compose.yml`, CI (линтер и тесты).
1. **Каталог.** Таблицы `components` и `manufacturers`, миграции, первые детали, `GET /components/{id}`.
2. **Поиск и фильтры.** Фильтры по JSONB, пагинация, полнотекстовый поиск, индексы, EXPLAIN ANALYZE.
3. **Совместимость и оценка.** Движок правил с табличными тестами, очки, «что потянет», узкое место, замена детали.
4. **Пользователи и фронтенд.** Регистрация, вход, сохранённые сборки, вводный урок и подсказки, страница сборки, CORS.
5. **Аналитика и квизы.** Рейтинг «очки за рубль» через оконные функции, медиана цен, аномалии и прогноз цен, отзывы, квизы.
6. **Наблюдаемость и кэш.** Redis, метрики Prometheus, дашборд Grafana.
7. **Микросервисы.** Выделение сервисов, gRPC, API gateway, трассировка (OpenTelemetry, Jaeger).
8. **События через Kafka.** `prices` → `notifications` («подешевело», «снова в наличии»), outbox, идемпотентность. ИИ-помощник отдельным сервисом.
9. **Kubernetes.** Деплой в локальный кластер (`kind`), пробы, Helm.

## Что тестировать особенно тщательно

- Правила совместимости: каждое правило табличным тестом, включая граничные случаи (ровно хватает мощности, видеокарта ровно по длине корпуса).
- Модель оценки и «что потянет»: пороги, нехватка памяти, узкое место.
- Подбор замены: только совместимые и доступные детали.
- Деньги: суммы сборки и цены без потери точности.
- Проверка прав доступа: пользователь не видит и не меняет чужие сборки.

## Безопасность

- Пароли только в виде хеша (argon2 или bcrypt).
- Секреты (включая ключ API для ИИ-помощника) только через окружение; в репозитории `.env.example`, а `.env` в `.gitignore`.
- Валидация всего ввода, проверка владельца при каждом обращении к записи, ограничение частоты запросов к ИИ-помощнику.
