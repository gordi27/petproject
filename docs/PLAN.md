# План проекта: личный финансовый помощник

Рабочее название: `petproject`. Веб-приложение для учёта расходов и доходов с расчётом накоплений. Проект учебный и для портфолио (позиция Go-разработчика), но задуман как приложением, которым автор пользуется сам.

## Цели

1. Вести расходы и доходы с гибкими категориями и метками, которые пользователь создаёт сам.
2. Считать всё по расчётным периодам между днями зарплаты (например, 15 и 30 числа), а не по календарным месяцам.
3. Показывать обязательные отложения на подписки и регулярные платежи на каждый период.
4. Считать средние и медианные траты по категориям, меткам и группам.
5. Помогать копить: считать, сколько реально можно откладывать, и прогнозировать срок достижения целей.

Попутно осваиваем навыки, нужные Go-разработчику: REST API, PostgreSQL, миграции, аутентификация, горутины, тесты, Docker, CI, затем Kafka, Kubernetes и frontend.

## Функциональные требования

### Категории и метки
- Пользовательские категории расходов и доходов (с вложенностью по желанию), свои названия и цвета.
- Группы меток, создаваемые пользователем. Примеры: «Канал» (онлайн/офлайн), «Необходимость» (обязательная/для удовольствия), «Периодичность» (разовая/подписка/ежемесячная).
- На каждую группу у операции не больше одного значения. Ограничение обеспечивается и в БД.
- Статистика по любой группе и метке.

### Расчётные периоды
- Пользователь задаёт дни выплат (например, 15 и 30). Период идёт от одной выплаты до следующей (15–29 и 30–14).
- Особые случаи: в коротких месяцах нет 30-го числа, берём последний день месяца; смена дней выплат в будущем без потери истории. Опционально: перенос выплаты с выходного на рабочий день.
- Отчёты, бюджеты и прогнозы считаются по периодам.

### Регулярные платежи и обязательные отложения
- Правила повторения: подписки, аренда, лекарства и т. п. (сумма, день, периодичность: месяц, год, раз в N дней).
- На каждый период приложение вычисляет предстоящие платежи и показывает список обязательных отложений на дату выплаты и общую сумму.

### Статистика
- Среднее и медиана по категориям, группам и меткам за последние N периодов (по умолчанию 6).
- Разделение регулярных и разовых трат, чтобы крупная покупка не искажала средние.
- Динамика по периодам и сравнение с предыдущим.

### Помощник по накоплениям
- Сколько реально можно откладывать = доход за период − обязательные отложения − средние траты «для удовольствия».
- Для каждой цели: сколько откладывать с каждой выплаты и когда цель будет достигнута (оптимистичный и пессимистичный варианты по медиане и среднему).
- Предупреждение, если сумма и срок цели нереальны.

### Прочее
- Регистрация и вход, данные каждого пользователя изолированы.
- Импорт банковской выписки из CSV и автокатегоризация по правилам.
- Бюджет (лимит) на категорию на период.

## Схема данных (набросок)

```
users(id, email, password_hash, ...)
accounts(id, user_id, name, currency, ...)
categories(id, user_id, parent_id, name, kind)            -- kind: expense | income
tag_groups(id, user_id, name)
tags(id, group_id, name)
transactions(id, user_id, account_id, category_id,
             amount_minor BIGINT, occurred_on DATE, note,
             recurring_rule_id NULL)
transaction_tags(transaction_id, tag_id)                  -- уникально по (transaction, group)
income_schedule(id, user_id, day_of_month, valid_from)
recurring_rules(id, user_id, category_id, amount_minor, frequency,
                day_of_month, starts_on, ends_on NULL)
goals(id, user_id, name, target_minor, deadline NULL, saved_minor)
```

Решения:
- Деньги хранятся целыми в минимальных единицах (копейки, `int64` / `BIGINT`), никаких `float64`.
- Даты операций: `DATE` без времени. Для версии 1 одна валюта.
- Уникальность «одно значение метки на группу у операции» обеспечивается в БД, не только в коде.

## Архитектура

Монолит с чёткими пакетами, которые потом можно выделить в сервисы:

```
cmd/server/            точка входа
internal/accounts/
internal/transactions/
internal/categories/   (и tags)
internal/periods/      календарная логика расчётных периодов
internal/recurring/    правила повторения, ближайшие платежи
internal/stats/        средние, медианы, динамика
internal/goals/        цели и прогноз
internal/importer/     импорт CSV, автокатегоризация
internal/auth/
migrations/
```

Слои: handler → service → repository, зависимости передаются через интерфейсы.

6. Цели и прогноз накоплений.
7. Импорт CSV и автокатегоризация.

## Что тестировать особенно тщательно

- Календарная логика: периоды, конец месяца, високосный год, смена дней выплат.
- Расчёт обязательных отложений на период.
- Статистика с пустыми и неполными периодами, среднее против медианы.
- Округление денег и прогноз накоплений.
- Проверка прав доступа: пользователь не видит чужие данные.

## Безопасность

- Пароли только в виде хеша (argon2 или bcrypt).
- Секреты только через окружение; в репозитории `.env.example`, а `.env` в `.gitignore`.
- Реальные выписки и персональные данные в репозиторий не попадают; для тестов используются синтетические данные.
- Валидация всего ввода, проверка владельца при каждом обращении к записи, ограничение размера и типа загружаемых файлов.
